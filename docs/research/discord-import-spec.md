## Problem Statement

Users who keep their photo and video library in Immich cannot currently import Discord attachments through this project. They must download files and upload them manually, even though the existing Telegram integration already provides ingestion, archive extraction, deduplication, naming, and album routing.

Users need two deliberate, one-way import actions: sending attachments to the bot in a direct message, and selecting a message through Discord's Apps context menu to save its attachments to Immich. The personal message-menu action must work in supported servers and private conversations without requiring the bot to join every server.

## Solution

Extend the existing application with a thin Discord adapter that shares `IngestionPipeline`, `ImmichClient`, and `State` with Telegram. Each deployment targets one configured Immich account and authorizes Discord callers through a separate user-ID whitelist.

Support Discord bot DMs and a globally registered, user-installable Message Command displayed as Save to Immich, with the Chinese localization 保存到 Immich. Process every supported native photo, video, and archive attachment in the selected message. Default to the `Discord Inbox` album and original filenames, with configurable naming and album templates.

Reuse existing Immich assets for identical content across platforms, while still ensuring their association with the current target album. Preserve partial successes and allow manual retriggering to complete failed work. Persist caller-owned `IngestRecord` entries for `/status`, including results that outlive the original interaction's reply window; do not automatically resume unfinished imports after a restart.

Run Telegram only, Discord only, or both adapters in one process. Serialize ingestion batches while keeping status queries responsive. Discord uses Gateway for ordinary DMs and interactions, so deployment does not require a public HTTP callback.

## User Stories

1. As a whitelisted Discord user, I want to send photos to the bot in a DM, so that I can import them without a manual download-and-upload step.
2. As a whitelisted Discord user, I want to send videos to the bot in a DM, so that I can save them to my Immich library through the same workflow.
3. As a whitelisted Discord user, I want to send supported archives to the bot, so that their photos and videos can be imported together.
4. As a whitelisted Discord user, I want to invoke Save to Immich on another person's message, so that I can save attachments I can already access.
5. As a Discord user, I want a message-menu action to process all supported attachments in the target message, so that I do not need to select each file separately.
6. As a Discord user, I want to install the application to my user account, so that I can use its message command without adding the bot to each server.
7. As a Discord user, I want to save attachments from a supported server conversation, so that server membership of the bot is not a prerequisite for my manual action.
8. As a Discord user, I want to use the message command in the bot DM, so that both supported entrypoints behave consistently.
9. As a Discord user, I want to use the message command in other DMs and group DMs, so that personal installation covers private conversations as well.
10. As a deployment operator, I want authorization to check the person sending the DM or invoking the menu, so that the target message's author does not determine who may use my Immich credentials.
11. As a deployment operator, I want unauthorized Discord users to be unable to trigger downloads or imports, so that only my configured whitelist can use the integration.
12. As a deployment operator, I want every authorized caller to import into one configured Immich account, so that the deployment remains simple to manage.
13. As a library owner, I want Discord imports to default to `Discord Inbox`, so that I can distinguish them from other ingestion sources.
14. As a library owner, I want to configure the Discord album name, so that I can choose an existing or automatically created destination album.
15. As a library owner, I want album templates based on normalized message metadata, so that I can organize imports by source or date.
16. As a Discord user, I want attachments to retain their original filenames by default, so that the saved files remain recognizable.
17. As a library owner, I want configurable Discord filename templates, so that I can opt into consistent naming without changing Telegram's defaults.
18. As an archive sender, I want extracted media to retain their entry filenames, so that archive contents remain recognizable after import.
19. As a template user, I want server imports to identify the original server and channel where names are available, so that generated names describe the source conversation.
20. As a template user, I want missing server or channel names to fall back to the corresponding IDs, so that imports work without additional bot membership or permissions.
21. As a template user, I want private-message sources and the sender field to identify the target message's author, so that saving someone else's message does not misattribute it to me.
22. As a library owner, I want message IDs and message timestamps to come from the selected source message, so that clicking Save later does not replace its source context.
23. As a library owner, I want photos with readable EXIF dates to retain the existing capture-date behavior, with message time as fallback, so that the integration does not introduce a second date policy.
24. As a library owner, I want identical files sent through Telegram and Discord to reuse one Immich asset, so that using both platforms does not duplicate my media.
25. As a library owner, I want files with different bytes to remain distinct even if they look alike, so that content deduplication does not silently discard modified versions.
26. As a Discord user, I want distinct attachments in one message to be imported independently, so that completing the first attachment does not cause the rest to be skipped.
27. As a Discord user, I want repeated saves of the same message, including saving a bot DM after automatic ingestion, to avoid another upload, so that retriggering is safe.
28. As an archive sender, I want archive entries and their enclosing attachment to have stable source identities, so that retrying an archive does not duplicate successful entries or collide with another archive.
29. As a library owner, I want an existing asset to be added to the current target album, so that deduplication still fulfills the new save request.
30. As a Discord user, I want an album-association failure to be reported separately from a successful upload, so that I can tell what remains unfinished.
31. As a Discord user, I want to retrigger an import to repair a failed album association without uploading successful files again, so that a temporary album error does not require manual library repair.
32. As a Discord user, I want successful attachments to remain saved when another attachment fails, so that useful progress is preserved.
33. As a Discord user, I want to retry failed work by invoking the menu again or resending attachments, so that recovery uses the same familiar entrypoints.
34. As a Discord user, I want menu responses to be visible only to me, so that import results are not posted to the source conversation.
35. As a Discord user, I want DM imports to receive their result in the bot DM, so that feedback stays with the files I sent.
36. As a Discord user, I want results to report new uploads, duplicates, skipped items, and errors with filenames and brief reasons, so that partial outcomes are understandable.
37. As a Discord user, I want `/status` to show my five most recent ingestion records, so that I can inspect recent requests without searching earlier replies.
38. As a Discord user, I want status queries to show only records belonging to me, so that other callers' imports are not exposed.
39. As a Discord user, I want an import to continue after the menu reply window expires and leave a queryable result, so that a slow upload does not lose its outcome.
40. As a Discord user, I want completed results to remain queryable after a service restart, so that restarting does not erase import history.
41. As a Discord user, I want a restart to mark unfinished imports interrupted, so that I know to trigger another import instead of assuming the work resumed.
42. As a deployment operator, I want a configurable Discord attachment limit defaulting to 2000 MiB, so that oversized inputs are refused with a clear explanation.
43. As an archive sender, I want a configurable limit defaulting to 1000 media files per archive, so that batches have a predictable bound.
44. As an archive sender, I want a media-count overflow to reject the whole archive before uploading its entries, so that an apparently successful import does not silently omit the remainder.
45. As an archive sender, I want media in ordinary subdirectories to be included, so that I do not need to flatten the archive first.
46. As an archive sender, I want non-media entries to be skipped and password-required archives to report an error, so that unsupported contents have explicit outcomes.
47. As an archive sender, I want nested archive files to be skipped rather than recursively expanded, so that the supported extraction boundary is predictable.
48. As a deployment operator, I want Telegram-only, Discord-only, and combined modes, so that I can run only the platforms I need.
49. As a deployment operator, I want Discord-only mode to work without Telegram credentials or a Telegram Bot API container, so that Discord does not inherit an unrelated setup requirement.
50. As an existing Telegram user, I want the old configuration, naming defaults, media handling, localization, and stored identities to remain usable, so that adding Discord does not require a migration of my usage habits or a reimport of history.
51. As a deployment operator, I want the enabled adapters to share one application process and ingestion core, so that I do not need to operate a second ingestion service or public callback endpoint.
52. As a Discord user, I want status queries to respond while imports wait or run, so that serialized ingestion does not make the bot appear unresponsive.
53. As a Discord user, I want supported interaction locales to use the existing reply languages and ordinary DMs to fall back to the configured default language, so that the new adapter has consistent localization behavior.

## Implementation Decisions

- **Transport boundary:** add a thin Discord adapter alongside the existing Telegram adapter. Both normalize source context into `MessageMetadata` and local files into `IngestItem`; `IngestionPipeline` remains responsible for extraction, content deduplication, Immich upload, album routing, and completion. Prefer `discord.py` for its context-command and installation-context support, subject to checking the selected release against the project's Python requirement.
- **Installation and delivery:** register the Message Command and `/status` globally for user installation and the agreed guild, bot-DM, and private-channel contexts. Receive interactions and ordinary bot DMs over Gateway, enabling the DM event intent. The two agreed entrypoints do not require general server-message monitoring or privileged Message Content access. Do not assume user installation grants historical-message or arbitrary server-resource access.
- **Authorization and target account:** retain one configured Immich account per deployment. Discord has its own caller-ID whitelist, separate from Telegram IDs. Check the invoking user or DM sender before downloading; the selected message's author is metadata, not the authorization principal. Apply the same caller ownership rule to `/status`.
- **Discord input normalization:** share attachment selection, size validation, source-URL download, metadata extraction, and local-item creation between DM and menu entrypoints. Accept supported native photo, video, and archive attachments only. Download source attachment URLs, retain required signature parameters, and do not assume a permanent URL or permission to refresh the message later. Missing optional MIME metadata must not by itself prevent a supported filename from being handled.
- **Source identity:** extend `IngestItem` and completion state to distinguish the platform, source channel/message, and individual attachment. Archive media also require stable entry identities within the enclosing attachment. Do not use an interaction ID, display name, or current batch order as the sole identity. Keep the existing Telegram identities and stored completion/content records compatible.
- **Content identity:** retain the existing exact-content deduplication approach and shared content-to-asset mapping. Source identity prevents repeated processing of the same inbound file; content identity reuses the Immich asset across different source files and platforms. This is not visual or perceptual matching.
- **Album completion:** associate newly uploaded and reused assets with the current resolved target album. An already-processed source must not bypass a required current album association. Record enough asset and association outcome to let a manual retrigger finish album work without reuploading successful media. Album creation or association failures are observable import errors, rather than log-only warnings; preserve assets already created.
- **Batch outcomes:** `IngestBatch` groups one import request's items. Extend `IngestSummary` as needed to expose skipped items and filename/stage-specific errors alongside new uploads and duplicates. An asset uploaded successfully can also have an album-association error; feedback must distinguish these phases rather than imply the upload failed or count every outcome as a disjoint input-file category. A failed attachment does not roll back successful attachments.
- **Naming and AlbumRouting:** Discord defaults to original attachment filenames and `Discord Inbox`. Keep Discord defaults/configuration independent of Telegram's existing defaults, while reusing the common template renderer. Resolve the target album from the outer message context for an archive and retain extracted media entry filenames. Preserve existing extension, sanitization, timezone, and fallback behavior.
- **MessageMetadata:** use the target message's ID and timestamp. For server messages, source is server name or ID joined with channel name or ID; for private messages, source is the original author's display name or username. The sender is the original author, not the command caller. Keep EXIF-first media date handling with the existing message-time fallback. Missing names must not add a requirement to install the bot in the server.
- **Attachment limits:** default the Discord attachment input limit to 2000 MiB, with one MiB equal to 1024 × 1024 bytes. Make it configurable. Reject a known oversized attachment before downloading, enforce the actual byte limit during download as well, and explain a mismatch or overflow. These are local input limits, not Discord reply-upload limits.
- **Archive limits and semantics:** retain the existing ZIP, RAR, 7z, and tar-family support through the existing archive mechanism. Scan ordinary extracted subdirectories for supported media, skip non-media and nested archives, and report password-required or extraction failures. Default to at most 1000 eligible media files per archive, configurable. Check for media-count overflow before uploading any entry from that archive and reject the whole archive on overflow; other attachments in the batch may still succeed. Input size and media-count limits do not represent a total decompressed-byte quota.
- **Queryable records:** persist `IngestRecord` data in the existing SQLite state, including the requesting caller, source/batch identity, lifecycle, timing, outcome counts, and meaningful errors. Records are query history, not durable execution instructions. Show the caller's five most recent records through `/status`, including waiting/running and terminal outcomes. On application startup, convert unfinished records from the previous run into interrupted records; do not replay them.
- **Interaction feedback:** acknowledge menu interactions promptly with a private deferred response, before long-running work. Update that response when possible; if the original reply window has expired, continue ingestion, persist its result, and let the caller query `/status`. DM imports reply in their DM. Do not add unsolicited completion DMs.
- **Runtime and concurrency:** one application-owned runtime starts only the configured adapters and owns shared clients/state and shutdown. Serialize ingestion batches across the enabled platforms to keep content deduplication consistent. Keep `/status` outside the ingestion serialization wait. In-memory waiting does not imply restart recovery; both enabled adapters restart with the common process.
- **Configuration and deployment:** support Telegram only, Discord only, and both, with validation limited to enabled-platform requirements. Retain the existing Telegram configuration entrypoint/default behavior and avoid requiring the Telegram Bot API service in Discord-only deployment. Update container composition, startup, health checks, and operator documentation consistently.
- **Language and local resources:** reuse the existing language catalog and default language configuration, formatting responses for the destination platform. Resolve supported Discord interaction locales where available, and use the default language for ordinary DMs without locale metadata. Preserve existing Telegram language and local-file cleanup contracts and ensure new download paths do not orphan temporary files.
- **Architecture records:** follow ADR-0001's deep ingestion module, ADR-0002's normalized naming/album boundary, and ADR-0003's existing localization approach. ADR-0004 establishes cross-platform source/content identity and album completion; ADR-0005 establishes the shared runtime and queryable records without automatic recovery. The deliberate behavioral correction is that duplicate assets receive album association and album failures become actionable outcomes.

## Testing Decisions

- **Confirmed boundary:** the user confirmed that the main automated acceptance seam is the existing `IngestionPipeline.ingest` entrypoint, using real temporary SQLite state and a simulated Immich boundary. Add only necessary Discord-entrypoint contract tests and real-account integration checks, not a new seam for each helper.
- **Good tests:** submit representative inputs and assert observable `IngestSummary`, stored completion/record behavior, Immich asset/album effects, and caller-visible responses. Avoid assertions about private helper calls, SQL shape, task scheduling internals, or an implementation-specific decomposition. Use bounded clocks/events instead of waiting for real interaction expiry.
- **Prior art:** reuse the existing pipeline tests' temporary state and simulated Immich fixtures, single-file and archive ingestion scenarios, safe retry after partial archive failure, dynamic album grouping, and cleanup coverage. Existing adapter-normalization, naming, configuration, localization, and HTTP-transport tests provide patterns for narrow contracts. Update the old log-only album-failure expectation to reflect the agreed actionable error behavior.
- **Core ingestion cases:** distinct attachments sharing one source message; repeated source attachments; platform/source isolation; identical bytes across Telegram and Discord; different bytes remaining distinct; archive entry identity; repeated DM/menu triggers; original filenames and configured naming/album templates; duplicate assets added to a second target album; upload and album failures preserved separately; and retry completing only missing work.
- **Archive and limit cases:** supported media in subdirectories, non-media/nested entries skipped, password-required and invalid archives, no eligible media, exactly-at-limit and over-limit input sizes/media counts, and proof that an oversized-media-count archive uploads no entries. Exercise declared and actual download sizes through the adapter contract. Include representative real archive fixtures through the ingestion boundary rather than relying only on mocked extraction.
- **State and query cases:** reopen real temporary SQLite state to verify persisted results; limit `/status` to five recent caller-owned records; hide other callers' records; mark stale unfinished records interrupted; do not resume them; and let a manually retriggered batch reuse successful assets and complete a pending album association. Preserve legacy Telegram source/content state during upgrade.
- **Discord entrypoint cases:** authorized and unauthorized DM/menu callers; target author distinct from invoker; all supported attachments selected; unsupported inputs reported as skipped; missing names falling back to IDs; missing optional MIME data; private menu defer/results; DM replies; expired interaction responses with continued processing and queryable results; and temporary download cleanup under the agreed cleanup policy.
- **Runtime and regression cases:** Telegram-only, Discord-only, and combined startup requirements; Discord-only operation without Telegram credentials/service; shared ingestion serialization without blocking status queries; and existing Telegram naming, supported-media, localization, state, and cleanup behavior. Validate configured local limits without treating the bot's Discord reply-upload allowance as a cap on an existing target attachment.
- **Real-account acceptance:** verify a user-installed application in a server the bot has not joined, the bot DM, another DM, and a group DM; normal DM attachment delivery over Gateway; source-name/ID fallbacks; private replies when external-app permissions restrict public replies; representative photo/video/archive downloads; and a long-running import whose final result is available through `/status`. Confirm developer-portal installation/distribution settings as part of this acceptance, not as an assumed API result.

## Out of Scope

- Per-user Immich accounts, OAuth binding, or storage of multiple users' Immich credentials in one deployment.
- Immich-to-Discord export, two-way synchronization, deletion propagation, or historical-channel harvesting.
- Watching arbitrary server conversations or other people's private messages without an explicit supported action.
- Selecting individual attachments after invoking the message menu, or choosing a target album interactively.
- Downloading external webpages, embed previews, stickers, or media inside Discord forwarded-message snapshots.
- Recursive nested-archive extraction, archive password input, or importing the archive itself as an Immich media asset.
- Perceptual/similarity deduplication, transcoding, or a new media metadata/date interpretation policy.
- Automatically replayed persistent queues, automatic restart recovery, or a new automatic retry scheduler; users retrigger failed or interrupted work.
- Parallel ingestion workers, independent adapter processes/restart domains, a generic platform plugin framework, or an additional public callback/admin service.
- Proactive completion DMs or a separate notification channel beyond the agreed entrypoint replies and `/status`.

## Further Notes

- This spec synthesizes the four confirmed decision rounds Q1–Q18 and the separately confirmed testing boundary on 2026-10-30. Invoking `to-spec` requests specification/publication; it does not assert that feature implementation or real-account acceptance has already happened.
- Discord's Message Command targets a whole message and appears in the Apps context menu. It does not provide native selection of one attachment within that message.
- Discord attachment URLs are signed and expire. User installation does not guarantee later permission to refetch the target message. Prefer timely local download and a fresh user-triggered action for a later retry rather than assuming a stored URL is permanent.
- Discord requires an initial interaction response within 3 seconds and interaction reply tokens expire after 15 minutes. These limits motivate the private deferred response and persistent status results; they are not an execution deadline for ingestion.
- Attachment upload limits vary independently of this project's local download cap. Do not use an interaction's reply attachment allowance to reject an existing selected attachment merely because its original author had a different upload allowance.
- The existing implementation has specific gaps this feature must close: source completion currently treats a message as a single file; asset-source prefixes are Telegram-specific; duplicate content bypasses album association; album errors are only logged; the configured archive-size limit is not enforced; and the archive media-count limit silently truncates. These observations are code-review evidence, not completed fixes.
- The original 4–6 person-day feasibility estimate preceded the full `/status` and retryable-album requirements; it is not a delivery commitment for this complete spec.
